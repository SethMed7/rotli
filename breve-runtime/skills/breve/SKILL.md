# BREVE

the maintainer's personal brief engine. Two modes, routed by the argument.

## Repo write policy (HARD RULE — overrides everything below)

Breve is an **observer**. It writes ONLY within three roots: its own repo **`{{BREVE_HOME}}`** (brief outputs in `{{BREVE_HOME}}/briefs/`, config, scripts), the knowledge base **`~/memex-vault`** (capture-routing via `~/memex-vault/inbox.md` and llmWiki updates), and working assets **`~/memex-vault/storage`** (binaries: PDFs, audio, PNG views). It reads locally ONLY those three roots — the sandbox enforces this. **All other code/repo insight comes from GitHub via `gh` (read-only) and the web — it never reads local project folders (`~/smLab`, `~/northstar/*`, or anything else).** If Breve notices something that *should* change in another repo (stale dashboard, broken link, anything), it FLAGS it in the brief for the maintainer — it never fixes it.

## Output appearance (owned by Rotli)

Rotli → Breve → Configure selects the PDF palette. Charcoal is the default;
Warm Light, Warm Dark, Paper, and a contrast-checked custom palette are also
supported. The renderer in `scripts/render-brief.ts` reads this setting. Agents
write Markdown only and never copy, restyle, or hand-write the HTML/PDF template.
Typography and print behavior remain defined in `{{BREVE_HOME}}/docs/theme.md`.

## Mode 1 — Daily brief (`/breve`, no args)

1. **Load config + state.** Read `{{BREVE_HOME}}/watchlist.md` (report through the lenses, not generic headlines). Most recent file in `briefs/` sets the "since last brief" window; first run or >14 days → last 7–14 days.
   **Drain the inbox:** `~/memex-vault/inbox.md` — route entries (watchlist → `{{BREVE_HOME}}/watchlist.md`, project notes → `~/memex-vault/wiki/projects/`, research → `~/memex-vault/wiki/research/`, personal facts → `~/memex-vault/self/` files, reminders → surface in this brief), clear processed, `?`-prefix ambiguous ones and ask when presenting. Commit routing changes. memex-vault is an llmWiki now — see `~/memex-vault/STRUCTURE.md`; binaries go to memex-vault/storage via `storage:` (never into memex-vault).
2. **Fan out research agents in parallel** (one message, all Agent calls at once), one per cluster: AI labs & coding agents · JS ecosystem · companies & infra · open-weight models · security & privacy · personal (chess + creators). Each: WebSearch/WebFetch, window-bounded, structured items (`title — date — source URL — 2-3 sentence summary — lens takeaway`), bar = "the maintainer would stop scrolling", empty result valid.
   **RECENCY GUARDRAIL (hard rule):** every industry/news item MUST carry (a) a real source URL and (b) a publication date that falls inside the since-last-brief window — drop anything you can't date to the window. **Never restate the watchlist's own example figures as if they were today's news** — the numbers in `watchlist.md` (e.g. the Miasma 473-artifact count, MiniMax's SWE-Bench 59.0% score) are static lens illustrations, NOT fresh events; only report them if a NEW, dated source in this window moves them. When in doubt, verify the item is genuinely new before it earns a spot; an empty cluster beats a stale or undated one.
3. **Scan repo activity via GitHub (READ-ONLY) — never the local folders.** The sandbox denies reading `~/northstar` and `~/smLab`, so pull repo movement with `gh`: `gh search commits --author=@me --sort=committer-date` (or `gh repo list` then `gh api repos/{owner}/{repo}/commits?since=<window>` / `.../pulls?state=all`) across the repos the maintainer can access, window-bounded; summarize movement in plain language. **memex-vault is the exception — read it locally** (it's a policy root). **smLab drift check (now GitHub-sourced):** if smLab had commits in the window, read `smlab-overview.html` via GitHub (`gh api repos/{owner}/{repo}/contents/smlab-overview.html --jq .download_url` then fetch, or the raw URL) and compare the "last updated" stamp in its `#status` section against the latest meaningful change — if the dashboard is older, flag it in the brief's projects section ("dashboard stale — update smlab-overview.html"). If smLab isn't on GitHub / the file can't be fetched, drop the check (note it's GitHub-sourced now).
4. **Compose** (5–10 min read, ruthlessly curated). **VOICE — write it like a sharp, friendly blog update, not a terse wire/data-dump:** flowing, readable prose with connective narrative between items, full sentences and short paragraphs over clipped fragments — like a knowledgeable friend catching the maintainer up over coffee. Keep every concrete number, date, and source, but deliver them inside natural prose; warm and direct, never padded. **TONE — informational and forward-looking, never alarmist:** the brief's job is to help the maintainer *stay ahead of the curve*, not to frighten him. Lead `## Headline` with the single biggest or most interesting story of the day — usually a major AI/model/company/ecosystem move, almost never a security item. Security is ONE beat among many: cover real, actionable vulnerabilities proportionally (in their own section + Action Items), but do NOT let warnings dominate the headline or the overall register. Prefer "here's what's emerging and why it matters" over "here's what to fear." **REQUIRED HEADERS (exact, in order — these are mandatory, the renderers parse them):** open with `## Headline` (one short paragraph: the single biggest thing — NOT a list, NOT a date line), then `## Action Items` (a markdown bullet list; bold the imperative in each, e.g. `- **Do X** — why`), then the industry sections (only where real news) → your projects → personal → "worth your time" (1–3 links) → **📡 Radar**: ONE company/project/tool NOT already on the watchlist but adjacent to its lenses (check `watchlist.md` first), 2–3 sentences on what it is and why it fits what he watches — encountered in this window's research is ideal. `render-brief.ts` renders `## Headline` as the lede and `## Action Items` as the alert box, and `send-brief.ts` builds the email from those two sections — so the exact headers `## Headline` and `## Action Items` are non-negotiable; without them the wrong headline gets picked. Also write `briefs/YYYY-MM-DD.suggestion.json` as `{"name": "...", "why": "<one line>"}` — the Signal morning send turns it into a yes/no question and a "yes" routes it into the watchlist. Skip Radar (and the json) if nothing genuinely fits; never pad. Slow week = short brief; never pad.
5. **Save `briefs/YYYY-MM-DD.md` — MARKDOWN only.** **REQUIRED — exact headers in order:** the saved file MUST use `## Headline` (one short paragraph, not a list, not a date line) then `## Action Items` (a markdown bullet list, imperative bolded) before the industry/projects/personal/Worth-Your-Time/📡 Radar sections. `render-brief.ts` renders `## Headline` as the lede and `## Action Items` as the alert box, and `send-brief.ts` builds the plain-text email summary from those two headers — so they are mandatory and must be spelled exactly. You do NOT write the HTML or PDF. Breve renders the readable, light blog/newsletter HTML + PDF from your markdown via `scripts/render-brief.ts` (the wrapper runs it on the 8 AM run; for an interactive `/breve` run, run it yourself: `bun {{BREVE_HOME}}/scripts/render-brief.ts YYYY-MM-DD` → writes `briefs/YYYY-MM-DD.html` + `$HOME/memex-vault/storage/brevePDFs/YYYY-MM-DD.pdf`). So **every source/video citation must be a markdown link `[Source name](url)`** in the `.md` (link the name, e.g. "The Register", "YouTube" — never a bare URL) so it survives into the rendered HTML/PDF as a clickable link; the maintainer clicks through from the PDF. Do NOT hand-write HTML or a theme template — presentation (and the masthead, which has no issue number) is owned by `render-brief.ts`.
6. **Present** the full brief in chat + PDF path.
7. **Audio digest:** `bun {{BREVE_HOME}}/scripts/audio-brief.ts` turns the markdown into `~/memex-vault/storage/breveAudios/YYYY-MM-DD.mp3` (the storage lane; the spoken script text lands beside the brief as `briefs/YYYY-MM-DD.audio.txt`) (~5 min three-host spoken digest; local Gemma writes a script with `[[anchor]]`/`[[security]]`/`[[personal]]` voice markers, multi-voice Kokoro TTS via `scripts/tts.ts` voices it — fully on-device, no keys; security/action items always land in the male voice). The 8 AM wrapper runs this automatically after the brief; for an interactive `/breve` run, generate it only if the maintainer asks. On-demand researched audio on any topic: `bun {{BREVE_HOME}}/scripts/audio-topic.ts "<ask>"` (Sonnet researches read-only, output in `briefs/topics/`).
8. **Delivery (8 AM run — all handled by the wrapper `morning-brief.sh` after the brief is saved; do not send from inside the scheduled run):** audio mp3 → the maintainer's Signal (`send-signal-brief.ts`, includes the Radar yes/no question); PDF → email (`send-brief.ts`, PDF only — no mp3); full-page PNG (`npx playwright screenshot`) → saved for Signal's inline `/brief` view. Outside the 8 AM run, email only on the maintainer's ask. (The email body is a short PLAIN-TEXT summary built from the `.md` by `send-brief.ts` — headline + action-item titles — with the readable PDF attached; no HTML structure to preserve.)

## Mode 2 — Topic brief (`/breve <topic>`)

A deep, on-demand brief on one subject (e.g. "/breve local-first sync engines", "/breve Corpay").

1. Decompose the topic into 3–5 research angles; spawn parallel agents (WebSearch/WebFetch; include local grounding — memex-vault/research/, repos — when the topic touches the maintainer's world). Same quality bar + citation discipline.
2. Compose a single-topic issue: what it is → what's new/true → what it means for the maintainer (through his stack/goals) → recommended next action → sources.
3. Save text to `briefs/topics/<topic-slug>-YYYY-MM-DD.{md,html}` using the configured PDF appearance (dateline reads `TOPIC BRIEF · <topic>` instead of an issue number); render the PDF to `$HOME/memex-vault/storage/brevePDFs/<topic-slug>-YYYY-MM-DD.pdf`. Present in chat; email only on request (send-brief.ts takes the date arg — for topic briefs pass the file stem).
4. If the topic deserves permanence, offer to file a distilled summary under `~/memex-vault/research/<topic>/`.

## Maintenance

"Watch X" / "stop watching Y" / lens corrections → edit `{{BREVE_HOME}}/watchlist.md` and mention it. PDF appearance changes are made in Rotli → Breve → Configure; do not edit renderer colors by hand.
